# 제어 연동 시뮬레이션 설계

## 문서 목적

Isaac Sim 씬을 정적 무대(v9)에서 시나리오 재생이 가능한 상태로 바꾸기 위한 설계 기준이다.
무엇을 실측에서 가져오고, 무엇을 모델로 선언하며, 씬이 무엇을 표현하는지를 분리해 기록한다.

선행 문서
- `스마트팩토리_씬_구성.md` 씬 도메인 선정과 초기 구성
- `gpu-spark2_Isaac-Sim_세팅.md` 실행 환경과 운영 명령
- 평가 설계의 권위 문서 §5 3트랙 × 2시나리오 (개발 저장소 존치, 비공개)

## 역할 분리

이 시뮬레이션은 DRATSN의 성능을 측정하지 않는다. 측정은 `../experiments/`가 담당하고,
여기서는 측정된 배치 결과를 시나리오로 재생한다.

| 구분 | 내용 | 출처 |
|---|---|---|
| 실측 | 고장 후 vPLC Pod가 어느 노드에 배치되는가, 재배치에 몇 ms 걸리는가 | `fig_twin` fault.csv (kind) |
| 실측 | TSN 경로 프레임에 VLAN/PCP가 실제로 부여되는가 | `fig_tagging` summary.csv |
| 모델 | 무보호 경로의 명령 지연 분포 | 본 문서에서 선언, λ로 스윕 |
| 씬 기하 | 작업 윈도우 길이, 컨베이어 속도, 부품 간격 | 씬 상수 |
| 산출 | 조립 성공 여부, 불량률, 누적 생산량 | 위 셋의 결합 결과 |

물리 PLC 트랙은 클러스터와 무관하다. 고정 배치와 교체 시간(1시간 하한)은 문헌 기반 **선언
파라미터**이며 측정값이 아니다.

실험 환경에 TSN NIC과 TSN 스위치가 없으므로 왕복 지연을 직접 재서 주입하는 방식은 채택하지 않는다.
그렇게 하면 측정된 지터가 TSN 유무의 차이가 아니라 실험 환경의 잡음을 반영하게 된다.
배치 결과는 TSN 하드웨어 없이도 정확하게 측정되며 kind 클러스터에서 동일하게 재현되므로,
주입 대상은 배치 결과로 한정한다.

## 입력 계약

`experiments/`가 생성한 CSV에서 기계적으로 유도한다.

```
scenario_feed.json
{
  "scenario": "fault",
  "compression": 60,
  "cells": [
    {"track": "physical", "events": [...]},
    {"track": "vanilla",  "events": [...]},
    {"track": "dratsn",   "events": [...]}
  ]
}
```

이벤트 항목

| 필드 | 의미 | 유도 방식 |
|---|---|---|
| `t_ms` | 압축 전 실시간 기준 발생 시각 | 시나리오 러너가 부여 |
| `kind` | `start` `fail` `reschedule` `resume` | 시나리오 정의 |
| `node` | 배치된 노드 이름 | 실측 CSV의 `node` 열 |
| `on_tsn` | 해당 노드가 TSN 경로를 보유하는가 | `node == TSN_NODE` |
| `tagged` | 데이터플레인 태깅 적용 여부 | 트랙 상수 |
| `sched_ms` | 배치 완료까지 걸린 시간 | 실측 CSV의 `sched_ms` 열 |
| `repair_ms` | 물리 PLC 교체 소요 시간 | 문헌 기반 파라미터, 하한 1시간 |

`tagged`는 측정 대상이 아니라 트랙 정의다. vanilla 트랙은 DRATSN이 없으므로 태깅이 존재하지 않고,
dratsn 트랙은 태깅이 존재하며 그 사실은 `fig_tagging`에서 이미 200/200으로 실증되었다.
따라서 태깅을 측정할 수 없는 kind 환경에서도 feed 생성이 가능하다.

## 경로 등급

배치 결과를 세 등급으로 환원한다. 등급이 명령 지연 분포를 결정한다.

| 등급 | 조건 | 의미 |
|---|---|---|
| P0 | `on_tsn` 이고 `tagged` | CNC가 배포한 GCL의 보호를 받는 구간 |
| P1 | `on_tsn` 이지만 `tagged` 아님 | 노드는 맞으나 PCP가 없어 best effort 큐로 처리 |
| P2 | `on_tsn` 아님 | 더 긴 best effort 경로 |

물리 PLC 트랙은 고정 배선이므로 항상 P0으로 두고, 대신 고장 시 교체 시간이 부과된다.
vanilla 트랙이 우연히 TSN 노드에 배치되어도 P1에 머문다는 점이 이 연구의 기여 구도에 해당한다.
배치 정확성과 데이터플레인 집행이 함께 성립해야 P0에 도달한다.

P1과 P2에 동일한 지연 분포를 적용한다. 개연성 문서는 P2가 더 긴 경로라고 서술하지만,
둘을 같게 두면 vanilla 트랙에 유리한 방향의 가정이 되어 주장이 보수적으로 유지된다.

## 지연 모델과 λ

무보호 등급의 명령 지연 `d`를 척도 파라미터 `λ`를 갖는 분포에서 추출한다.
`λ`는 측정값이 아니라 선언된 모델 파라미터이며, 논문에도 그렇게 명시한다.

```
P0        : d = 0          (GCL 보장 구간, 사이클 내 도착)
P1, P2    : d ~ Exp(λ)     (무보호 큐)
```

단일 `λ` 값을 고르면 그 값의 근거가 논쟁 대상이 되므로 전 구간을 스윕하고
"λ가 어떤 값이든 vanilla의 불량률이 dratsn보다 높으며 교차가 없다"는 형태로 제시한다.

## 씬 상수

v9의 고정 지형지물이 스테이션 격자를 이미 결정하고 있다. 로봇이 y = -0.85, 검사 게이트가
y = -2.65에 박혀 있고 그 간격이 1.80 m이므로, 이를 인덱스 피치로 삼으면 나머지 스테이션이
벨트 범위(y ∈ [-4.225, 2.925]) 안에 떨어진다. 컨베이어는 정속이 아니라 인덱스 방식이다.

| 상수 | 값 | 근거 |
|---|---|---|
| 스테이션 | 2.75 / 0.95 / **-0.85 작업** / **-2.65 검사** / -4.45 | v9 기하 |
| 인덱스 피치 | 1.80 m | 작업-검사 간격 |
| 사이클 | 24프레임 = 이동 10 + 정지 14 (24 fps) | 화면 1초 |
| 압축비 | 60:1 | 실시간 1시간 = 화면 60초 |
| 사이클 실시간 | 60초 | 압축 결과 |
| 정지(조립) 실시간 | 35초 | 압축 결과 |
| 재생 길이 | 120 사이클 = 화면 120초 = 실시간 2시간 | |

값은 `sim_model.py` 상단에 있고 씬 생성기가 그대로 가져다 쓴다.

## 조립 판정

접촉 물리와 집기 로직은 구현하지 않는다. 판정은 제어 사이클 단위로 이루어진다.

부품당 명령 1회로 두고 `d > W`를 실패로 보는 방식은 수치가 성립하지 않는다. 압축비 60:1에서
조립 정지 구간이 실시간 35초인데 명령 지연은 ms 단위여서 `P(d > W)`가 사실상 0이 된다.
제어 루프는 부품당 1회가 아니라 주기적으로 돈다는 점을 반영해야 한다.

```
T_cycle              제어 주기 (실시간 10 ms)
N = 정지시간 / T_cycle = 3500      부품 1개 조립 중 도는 제어 사이클 수
q(λ) = P(d > T_cycle) = exp(-T_cycle / λ)      d ~ Exp(λ)
결함  <=>  최대 연속 초과 런 길이 >= R  (R = 4)
```

고립된 지연은 궤적이 흡수하지만 연속 초과는 이탈을 만든다. 런 길이 분포에는 닫힌 해가 없고
DP로 계산해야 하므로, 접촉 물리가 없어도 시뮬레이션이 실제로 계산할 대상이 남는다.
λ에 대한 임계 비선형도 여기서 나온다. `R`은 `λ`와 함께 선언 파라미터이며 같이 스윕한다.

실측된 전이 구간은 λ ∈ [3, 7] ms다. 그 아래는 결함 0, 그 위는 전량 결함이 된다.

## 실패 표현

명령이 늦으면 결함 AGV가 컨베이어를 계속 타고 흐른다.
`agv_model(defective=True)`가 이미 바퀴 하나 누락과 커버 13도 틀어짐을 표현하므로 신규 자산은 필요 없다.

지연이 왜 결함으로 이어지는지는 화면만으로 곧바로 읽히지 않는다.
씬에 이미 존재하는 검사 게이트(`Inspection`, y = -2.65)를 판정 지점으로 사용해 인과를 잇는다.

**불량일 때만 점멸한다.** 정상품마다 녹색을 켜면 점멸이 배경 소음이 되어 적색 경보가 묻힌다.

렌즈는 지름 7.5 cm라 오버뷰에서 2 px 남짓이라 보이지 않는다. 판정을 실어 나르는 것은 게이트
위에 새로 단 **경보 패널**(1.30 × 0.42 m, 화면상 약 42 × 14 px)이고, 빔과 렌즈도 같은
머티리얼에 묶는다. 베이스 색은 어두운 회색이다. 안전 노랑을 그대로 두면 적색 발광이 노랑에
묻혀 주황으로 보이므로, 꺼진 램프처럼 어둡게 두어야 적색이 산다.

## 씬 변경 목록 (v9 → v10)

현재 v9의 좌표 체계를 유지한다. 셀은 x = 7.0(물리 PLC), 0.0(vanilla), -7.0(dratsn)에 있고
컨베이어는 +Y에서 -Y 방향으로 흐르며 로봇 두 대가 y = -0.85에서 마주본다.

### 1. 컨베이어 실제 이동

벨트 프림은 고정하고, 벨트 표면을 타고 흐르는 **플라이트 바**(`Conveyor/FlightBar_*`) 5개가
칸을 나누며 -Y로 이동한다. 제품과 같은 인덱스 스케줄을 따르므로 라인이 멈추면 같이 멈춘다.
벨트 밖으로 나간 바는 보이지 않게 하고 위쪽으로 되돌려 재사용한다.

v9의 흐름 화살표(`Conveyor/FlowArrow_*`)와 제자리 회전 롤러(`Conveyor/Roller_*`)는 둘 다
제거한다. 화살표는 실제 이동이 생기면 중복이고, 제자리에서 도는 롤러는 바퀴가 헛도는 것으로
읽혀 이동 방향을 오히려 흐린다.

바 두께는 오버뷰 카메라 기준 화면 크기로 정했다. 이 거리에서 1 m는 약 32 px이므로 v9의
0.07 m 부재는 2 px 남짓이라 보이지 않는다. 0.13 m로 키우고 밝은 색을 입혀 어두운 벨트와
대비시킨다.

### 2. 제품 스폰과 상태 전환

v9는 제품 네 개가 고정 좌표에 놓여 있다. 이를 스폰 방식으로 바꾼다.

| 구간 | 상태 | 프림 |
|---|---|---|
| 진입부터 작업 윈도우까지 | Parts kit | `agv_parts_kit` |
| 윈도우 통과 이후 | 정상 AGV 또는 결함 AGV | `agv_model(defective=False/True)` |

세 프림을 같은 위치에 겹쳐 두고 `visibility`를 시간축으로 토글해 전환한다.
상태 전환 시점에 로봇 동작 애니메이션이 겹치므로 교체가 드러나지 않는다.

### 3. 로봇 동작

집기와 조립 로직은 없다. UR10e의 손이 부품 쪽으로 내려왔다 복귀하는 고정 동작만 재생한다.
명령을 제때 받은 사이클은 부품까지 내려오고, 놓친 사이클은 중간에서 멈칫하다 만다.
로봇이 끝까지 내려오지 못하는 것 자체가 명령 미도달의 시각 신호다.

두 가지를 바로잡아야 동작이 성립한다.

**로봇 방향.** UR10e는 rest 자세에서 자기 +X로 1.18 m 뻗은 상태다. v9의 yaw(∓90도)로는 팔이
벨트를 가로지르지 않고 벨트를 따라 옆으로 뻗어 손이 부품 근처에 오지 않는다. yaw를 0도와
180도로 바꿔 두 로봇이 벨트를 사이에 두고 마주보게 한다.

**관절 구동 방식.** 이 에셋은 링크가 전부 `/ur10e` 아래 형제로 놓이고 그 사이를
`PhysicsRevoluteJoint`가 잇는 평면 구조다. 중첩 체인이 아니므로 각도 하나로 팔을 접을 수 없고,
링크 트랜스폼을 직접 덮어쓰는 방법만 남는다. 정식 순기구학 대신 **어깨를 축으로 팔 전체를
강체로 회전**시킨다. 베이스가 바닥을 뚫지 않으면서 손은 움직이므로 목적에는 충분하다.

각도는 기하로 정했다. 파킹 -32도에서 손이 z = 1.27로 벨트 레일 위를 지나고, -17도로 내리면
z = 1.01이 되어 부품 몸체(z ≈ 1.03)에 닿는다. 리치 1.17 m는 로봇과 벨트 중심 사이 거리
1.15 m와 맞는다.

관절 단위 구동은 여전히 2단계 과제다.

### 4. 경로 하이라이트

v9는 각 셀에 TSN(청색)과 best effort(주황색) 케이블이 모두 연결되어 있고 항상 같은 밝기다.
주입된 배치 결과에 따라 실제로 사용되는 경로만 밝게 표시한다. 머티리얼은
`UsdPreviewSurface`에 `emissiveColor` 입력을 추가하고 타임샘플로 밝기를 조절한다.

이 무대에서 랙은 스위치에 1:1로 배선되어 있다. Rack_A는 TSN 스위치로만, Rack_B는 best effort
스위치로만 올라간다. 따라서 **Pod 표식이 앉는 랙과 점등되는 케이블은 같은 선택이며, 둘 다
경로 등급을 따른다.**

| 경로 등급 | Pod 표식 | 케이블 |
|---|---|---|
| P0 | Rack_A | 청색 점등 |
| P1, P2 | Rack_B | 주황색 점등 |

한쪽 랙 위에 표식을 띄워 놓고 다른 랙의 배선을 켜면 화면이 자기모순을 일으킨다. 배치와 집행을
서로 다른 랙으로 나눠 표현하려면 랙마다 업링크를 따로 두는 토폴로지 변경이 필요하다.

이 배선 때문에 P1(TSN 노드에 얹혔으나 태깅 없음)과 P2(원격 노드)는 화면상 구분되지 않는다.
모델이 두 등급에 같은 지연 분포를 쓰므로 정량 결과에는 차이가 없고, 잃는 것은 서술뿐이다.

물리 PLC 셀에는 랙이 없고 PLC 캐비닛만 있으므로 청색 경로를 항상 활성으로 고정한다.

활성 표시는 세 가지를 겹친다. 색만 바꾸면 어느 방향으로 흐르는지 알 수 없는데, 방향이야말로
경로를 보여주는 이유이기 때문이다.

- 밝기: `emissiveColor`를 올린다
- 굵기: 케이블 `widths`를 0.055에서 0.105로 늘린다
- 방향: 스위치에서 로봇 쪽으로 흐르는 **패킷 표식** 3개가 사이클마다 배선을 한 번 훑는다.
  경로 머티리얼을 공유하므로 경로가 꺼지면 함께 어두워진다.

패킷은 배선 끝에 닿으면 숨었다가 시작점으로 되돌아온 뒤 다시 나타난다. 한 사이클의 마지막
샘플과 다음 사이클의 첫 샘플이 같은 타임코드를 쓰면 표식이 배선을 따라가지 않고 끝점에서
시작점으로 직선 보간되어 공중을 가로지른다. 왕복 구간을 5프레임 비워 두고 그 사이에 숨긴다.

### 5. Pod 재배치 표현

`PodAnimationAnchor`가 vanilla(x = -1.08)와 dratsn(x = -8.08)의 z = 2.85에 이미 준비되어 있다.
재배치 이벤트에서 Pod 표식이 원래 랙에서 대상 랙으로 옮겨간다.

재배치는 실측 기준 수백 ms이고 사이클은 실시간 60초이므로, 사이클 단위 판정으로는 이벤트가
보이지 않는다. 따라서 경로 하이라이트와 Pod 이동은 사이클이 아니라 **feed의 이벤트 시각에서
직접** 구동한다. 전환은 실제 프레임에 그대로 찍고, 그 뒤 14프레임 동안 목적지 경로에 잔광을
준다. 잔광은 눈이 따라갈 수 있게 하는 가독성 장치이며 지속 시간 주장이 아니다.

표식은 랙 위에서 위아래로 뜨면서 천천히 돈다. 정지한 표식은 랙에 붙은 스티커처럼 보여서
살아 있는 Pod로 읽히지 않는다. 앵커가 배치(어느 랙)를, 그 자식이 부유와 회전을 담당한다.
진폭은 0.22 m다. 0.075 m는 오버뷰에서 2 px라 움직임으로 보이지 않는다.

**표식의 위치와 색 모두 경로 등급을 따른다.** 표식을 TSN 머티리얼에 고정하면 보호받지 않는
트래픽이 보호색으로 칠해지고, 위치를 `on_tsn`으로 두면 켜진 케이블과 다른 랙에 떠 있게 된다.

현재 무대에서는 재배치가 경로 등급을 바꾸지 않으면 표식이 랙 사이를 이동하지 않는다. 이동
연출을 살리려면 존마다 노드 수만큼 랙을 두고 그중 하나만 TSN 업링크를 갖게 해야 한다. 그러면
비-TSN 노드 사이의 재배치도 랙 이동으로 보이면서 색은 주황을 유지한다. 미결정 항목이다.

### 5-1. 드레인 사이클

마지막 사이클에 투입된 부품도 작업 스테이션까지 가야 하므로, 생산 사이클이 끝난 뒤 신규 투입

수량이 일치한다.

### 7. 예비 셀

시나리오 B 착수 시 트랙당 예비 셀을 추가해 여섯 셀 구성으로 확장한다.
개연성 문서는 예비 셀을 무대에 사전 배치하고 활성화 방식으로 재생하도록 규정하므로,
B 단계에서 셀을 새로 만드는 것이 아니라 회색 비활성 셀을 미리 세워 두는 방향이 맞다.

다만 본 단계에서는 시나리오 A만 다루므로 세 셀 구성을 유지하고 좌표 슬롯만 상수로 예약한다.
확장 시 폭이 약 27 m에서 50 m로 늘어나 고정 카메라(eye 1.5, -31, 23 / focal 34)를 재조정해야 하고,
x = 12.45의 AGV 쇼케이스와 위치가 충돌하므로 함께 옮겨야 한다.

## 시나리오 A 장애

압축비 60:1을 전 구간에 동일하게 적용한다. 실시간 1시간이 60초에 대응한다.
구간별로 배율을 바꾸면 누적 생산량 곡선의 시간축이 왜곡되어 트랙 간 비교가 성립하지 않는다.

동일 확률의 고장 이벤트를 세 트랙에 동시에 주입한다.

| 트랙 | 고장 대상 | 이후 전개 |
|---|---|---|
| 물리 PLC | PLC 캐비닛 | 셀 정지, 교체 잔여 시간 카운터 표시, 카운터 소진 후 재가동 |
| vanilla | vPLC가 도는 노드 | 초 단위 재배치, 도착 랙에 따라 P1 또는 P2, 결함 발생 |
| dratsn | vPLC가 도는 노드 | 초 단위 재배치, 항상 TSN 랙, P0 유지 |

관측 지점은 세 가지다. 물리 PLC는 정지 구간의 길이에서, vanilla는 재개 이후의 결함 누적에서,
dratsn은 두 가지가 모두 나타나지 않는다는 점에서 차이가 드러난다.

- 정량 CSV 두 개. 씬이 애니메이션을 만들려면 사이클별 조립 성공 여부를 어차피 계산하므로
  파일로 남기는 비용이 없다. λ 스윕 결과를 곡선으로 제시하려면 필요하다.

sweep.csv    track,lambda_ms,threshold,produced,stopped,defect,defect_rate    (해석적, 시드 무관)

`sweep.py`는 실행 때마다 전 구간에서 dratsn의 불량률이 vanilla를 넘지 않는지(교차 없음)를
검사하고 위반하면 실패한다.

## 파이프라인

```
experiments/fig_twin/     kind 전용. fig_placement와 독립
  run_fault.sh                   노드 고장 주입 후 재배치 결과 수집 -> fault.csv
  build_feed.py                  fault.csv -> scenario_feed.json
  plot.py                        fault.csv -> f13_fault.png
  results/<RUN>/

isaac-sim/
  sim_model.py                   판정 모델. 표준 라이브러리만 사용
  sweep.py                       λ x R 스윕 -> sweep.csv, cycles.csv
  build_factory_scene.py         v10 씬 생성 + 타임샘플 굽기 (컨테이너에서 실행)
  render_frames.py               지정 프레임 headless 캡처
```

수집 (로컬, kind):

```bash
cd experiments/kind && ./create-cluster.sh && ./deploy.sh   # 최초 1회
cd ../fig_twin && TRIALS=10 RUN=myrun ./run_fault.sh
../.venv/bin/python build_feed.py results/myrun
../.venv/bin/python plot.py results/myrun
```

씬 굽기 (컨테이너 안, `/isaac-sim/Documents/dratsn_factory/scripts`):

```bash
python3 sim_model.py                       # 로컬에서도 가능. 모델 자체 검증
python3 sweep.py --out results/dev         # 로컬에서도 가능. λ 스윕 CSV

./python.sh build_factory_scene.py ../scene/factory_three_cells_v10.usda \
    --feed ../scene/scenario_feed.json --lambda 5.0
./python.sh render_frames.py ../scene/factory_three_cells_v10.usda \
    --frames 155,1000,2400 --out ../preview
```

`--feed`를 주지 않으면 `sim_model.default_fault_feed()`의 손수 만든 시나리오 A로 굽는다.
폴백일 뿐이고, 정상 경로는 `fig_twin`이 만든 실측 feed다.

`experiments/` 기존 규약과 동일하게 수집과 그림 생성이 같은 `results/<RUN>/`에서 완결되도록 한다.
